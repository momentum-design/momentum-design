# Overlays

Momentum's overlay family includes Dialog and AnnouncementDialog, Popover and
its derivatives (MenuPopover, Tooltip, Toggletip, Coachmark), and surfaces used
by components such as Select and SearchPopover.

## Layer ordering

Managed overlays use one resolved layer order for visual placement and
dismissal. Opening time determines the automatic z-index, but an explicit
`zIndex` property (or `z-index` attribute) also determines interaction order.

- An automatic overlay receives `1000 + 3 × registration index`.
- An explicit integer overrides that automatic value.
- Within the same managed parent context, the highest resolved value is on top.
- A DOM-nested overlay is above its managed ancestor even when its own value is
  lower. Its entire branch stays at the ancestor's level relative to unrelated
  overlays; a high child value cannot escape a lower ancestor's context.
- Equal values between branches follow DOM order when the hosts share a root:
  the later host is above the earlier one. Otherwise registration order breaks
  the tie.
- Changing `zIndex` while open reevaluates dismissal and eligible focus
  ownership without reopening the overlay. Removing the attribute returns to
  automatic ordering.

Registration bookkeeping is not sorted by resolved z-index. This avoids a
feedback loop between automatic values and their ordering. When an overlay is
removed, remaining automatic values are recalculated from their new registration
indices; explicit values do not change.

For example, opening an automatic Popover and then a Dialog with `z-index="1"`
leaves the Popover above the Dialog. Opening later does not give that lower
Dialog dismissal or focus ownership.

### Scope

This ordering applies to Momentum-managed layers in comparable CSS stacking
contexts. A numeric z-index cannot override ancestor stacking contexts or the
browser's native top layer. Momentum accounts for managed DOM ancestors, but it
does not infer global browser paint order.

Dialog stays where it is rendered. Popover also stays in place unless
`append-to` moves it into the identified container. Choose suitable containers
when escaping clipping ancestors; `append-to` does not make arbitrary stacking
contexts numerically comparable. Trigger nesting preserves cascading and focus
return, not CSS ancestry: a portaled overlay is ordered numerically where it is
actually placed.

### Backdrops and triggers

Each overlay retains these offsets from its resolved value:

- overlay: `zIndex`
- trigger, when raised above a Popover backdrop: `zIndex - 1`
- backdrop: `zIndex - 2`

An automatic first overlay therefore uses 1000, 999, and 998. The next uses
1003, 1002, and 1001. Explicit values retain the same offsets, including after a
live property change. Leave enough space between explicit values if their
backdrop/trigger bands must not overlap.

## Dismissal

Escape and outside-click handlers act only for the top managed layer, subject to
the component's dismissal settings. One event retains one dismissal owner, even
if closing that layer exposes another one during event propagation.

A component may also close through its close button, public visibility property,
or `hide()` method where supported. Component-specific events and controlled
visibility conventions are documented on the individual components.

## Nesting and lifecycle

Closing or disconnecting an overlay removes its genuinely nested descendants
within the same stack group. Nesting follows DOM containment and triggers inside
another overlay, including chains whose Popovers have been moved with
`append-to`. Current keyboard focus is not evidence of nesting.

Independent overlays are not descendants merely because they opened later or
have a higher z-index. Hiding either independent overlay leaves the other open,
regardless of opening order. This replaces the previous blanket rule that
closing an overlay also closed later same-group registrations.

### Same-trigger siblings

Multiple overlays can share an opener, such as a Tooltip and Popover. Set their
`triggerid` attributes to the same non-empty ID. Closing one does not cascade to
the other as a nested descendant.

```html
<mdc-button id="opener">Open details</mdc-button>
<mdc-popover triggerid="opener">...</mdc-popover>
<mdc-tooltip triggerid="opener">...</mdc-tooltip>
```

### Stack groups

The `stack-group-name` attribute limits descendant cascading. A nested overlay
in a different group is not removed by its ancestor's stack removal. Overlays
without a group use the default group (an empty string).

For example, a Dialog may contain a warning Popover in group `warning` and a
combobox dropdown in the default group. Dismissing the warning does not remove
the independent dropdown. Group membership does not change resolved visual order
or give an overlay focus ownership.

DOM removal still removes actual DOM children. Popover's `append-to` placeholder
also removes its moved Popover when the original containing subtree is removed;
a separate stack group does not override DOM lifecycle.

## Focus ownership

Only the highest eligible focus-managing layer has an active focus trap. A
higher non-focus-trapping Tooltip does not suspend the trap below it. Dialog's
`focus-trap` setting and Popover's `interactive` plus `focus-trap` settings
control eligibility.

Opening a lower eligible overlay registers its trap without moving focus away
from the higher owner. Changes to z-index or focus eligibility reevaluate the
owner. Initial focus and deferred activation respect that ownership.

When the focus owner closes, focus returns to its available trigger/previous
focus target if that target belongs to the resumed trap (or no trap remains).
For a portaled menu chain, restoration skips targets in removed layers and
follows trigger relationships to an available opener within the resumed trap.
Otherwise focus moves into the resumed trap.

An overlay owns focus for restoration when it is the active trap or contains the
actual focused element. This includes a non-trapping Popover inside a Dialog and
an ancestor whose child just restored focus during a cascading close. A lower
overlay that has neither ownership cannot restore focus on hide or disconnect.

Standalone FocusTrap components retain activation ordering. Inside a managed
overlay, they share its layer; the most recently activated trap within that
layer owns focus. Spatial navigation uses the same active trap as Tab
navigation.
